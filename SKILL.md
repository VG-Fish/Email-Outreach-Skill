# Email Workflow

Run a truthful, approval-gated customer, sponsor, partner, or professional outreach campaign. Use this mandatory sequence: clarify campaign and sender → define and approve target demographic → define the opportunity → choose an email-template direction → create approved campaign records → discover and rank the current user’s sources → find and qualify the requested number of recipients → personalize drafts → choose delivery method → place drafts or send only with approval.

## 1. Clarify campaign and sender

1. Establish the requested state: planning only, research only, chat drafts, email-account drafts, or approved sends. Default to planning and research.
2. Ask who the user is and how to represent them: name, organization/team/school, role, relevant proof points, location when relevant, preferred signature/contact details, and facts that must not be used. Do not invent any of these.
3. Ask whether the campaign seeks customers, sponsors, partners, investors, recruiting contacts, or another target type. Keep one primary ask per campaign lane.
4. Ask for `X`: the exact number of qualified potential recipients to find. Do not default to 10. If `X` cannot be reached without weakening qualification standards, return the qualified remainder and document the constraint.
5. Define the offer/ask, success condition, geography, timing, budget/range when relevant, exclusions, and desired campaign state.
6. State the non-negotiable constraint: never send an email unless the user has approved the exact current recipient, subject, body, attachments, sender identity, and send time for that recipient.

## 2. Define target demographic

Before finding recipients, ask the user to describe the target demographic. Cover only relevant dimensions: industry/category; organization size and maturity; geography; buyer/sponsor role and seniority; technical, mission, or audience alignment; budget/ability to support; brand values; event/program fit; and explicit exclusions.

If the user is unsure, propose one or more target-demographic hypotheses based on the user’s offer, opportunity, goals, and available evidence. For every hypothesis, state:

- Why it is likely to fit.
- Ideal organization characteristics.
- Likely decision-maker or internal champion.
- Expected value exchange.
- Exclusions and risks.

The user must approve, edit, or select a demographic before recipient discovery begins. Do not silently substitute the agent’s preferred demographic.

## 3. Define the opportunity

For sponsorship, partnership, event, or resource-request outreach, ask before preparing templates:

1. What upcoming event, competition, launch, conference, race, demo, fundraising activity, travel, or deadline is relevant? Capture name, date, location, audience, expected participation/attendance, and decision deadline.
2. What concrete team, project, program, event, asset, or activity can a company support?
3. What support is requested: cash, product, technical expertise, facilities, promotion, mentoring, recruiting presence, in-kind service, or another defined contribution?
4. What substantiated benefits/deliverables can the supporter receive? Examples may include logo placement, event recognition, demo access, recruiting interaction, approved content inclusion, naming rights, or impact reporting. Never promise exposure, access, attendance, rights, or deliverables the user cannot provide.
5. What evidence supports the opportunity: sponsor deck, budget, official event page, audience metrics, prior results, team page, media kit, or confirmed commitments?

If no concrete sponsorable opportunity exists, do not force a sponsorship angle.

## 4. Choose template direction

Before researching recipients, create two or three short template emails tailored to the approved sender profile, target demographic, and campaign ask. Templates are positioning options, not generic mail-merge messages.

Use legitimately distinct angles, for example:

- Direct value proposition/customer problem.
- Mission, technical, or audience alignment.
- Time-bounded event, program, or sponsorship opportunity.

For every template, show: intended recipient profile; subject; exact body; one concrete ask; positioning rationale; assumptions/facts needing confirmation; and `NOT SENT`.

Ask the user to select one template, modify one, or specify a combination of named elements. Do not find, rank, or contact recipients until the user approves the template direction. Use the approved template as a base while personalizing every final email; never send an identical generic mail merge.

## 5. Create campaign records

After the user approves the target demographic and template direction, prepare two synchronized campaign records:

1. A spreadsheet for structured data, pipeline status, source verification, ranking, contact paths, deduplication, and email versions.
2. A document for the campaign brief, approved target-demographic definition, opportunity details, approved templates, rationale, and readable research notes.

Select an appropriate connected office suite from the **current user’s** available connectors: Google Sheets/Docs when Google Workspace is connected; Microsoft Excel/Word/OneDrive/SharePoint when Microsoft 365 is connected; or another user-approved writable workspace. If no writable suite is connected, provide spreadsheet-ready and document-ready content in chat and state clearly that external records were not created.

Creating or updating external records is side-effecting. Before creating either record, resolve the platform, destination, filenames, sharing scope, and complete initial contents; then obtain explicit user approval. Create the records using the same campaign ID and cross-links/references where supported. Do not claim records were created until the connected tool reports success.

| Record element | Spreadsheet | Document |
| --- | --- | --- |
| Campaign brief and sender profile | Summary tab | Campaign brief |
| Approved target demographic | Criteria tab | Target-demographic section |
| Event/program and benefits | Opportunity tab | Opportunity section |
| Approved templates and versions | Templates tab | Templates section |
| Recipient research/contact paths | Targets tab | Research-note summaries |
| Status, ownership, dates, outcomes | Pipeline tab | Activity log/key decisions |

The spreadsheet is the operational source of truth for row-level status. The document is the readable narrative record. Update both after material changes when connected and authorized; preserve historical versions rather than overwriting evidence or prior sends.

## 6. Discover user-specific sources

Inspect the current user’s connected connectors after campaign context and template direction are approved. Identify sources relevant to this campaign and rank only connected, permitted sources by evidence quality, relevance, freshness, and duplicate-prevention value.

| Priority | Source category | Use it for |
| --- | --- | --- |
| 1 | Public web and official sources | Current roles, company priorities, opportunity evidence, authoritative contact paths, and personalization |
| 2 | Mailbox, calendar, CRM | Prior contact, replies, opt-outs, active sequences, ownership, meetings, and duplicates |
| 3 | Connected prospecting/enrichment tools | Candidate discovery, company fit, professional contact enrichment, and verification support |
| 4 | Shared files and collaboration systems | Existing relationships, prior proposals, brand voice, exclusions, sponsor materials, and internal context |
| 5 | Contact directories and delivery platforms | User-owned contacts, approved drafts, suppression status, and eventual delivery |

Treat Clay, Apollo, Hunter, RocketReach, Resend, Brevo, and comparable services as examples only. Check their status for the current user, not against a fixed global list. Report each relevant service as `connected`, `available but not connected`, `temporarily unavailable`, or `not available for this user`. Search only connected and relevant sources.

If a useful service is disconnected, continue with the next-best connected source unless it is essential to the stated goal; then explain what it adds and ask the user to connect it. Do not assume any connector exists, is searchable, or contains relevant information. Do not search private messages, private channels, or personal data unless the user authorizes that scope and the connector permits it.

## 7. Find and qualify X recipients

Find exactly the user-requested `X` qualified potential customers, sponsors, or other recipients where possible. A qualified recipient must demonstrably fit the approved target demographic and be able to buy, sponsor, influence, or credibly route the exact ask.

For every candidate:

1. Verify their current role and organization using a primary or official source where possible; record source and verification date.
2. Explain fit to the approved target demographic, the user’s real profile, and the specific offer or opportunity.
3. Find only legitimate professional contact paths: a user-supplied address, official directory/staff-page address, official press/contact address, or clearly public professional address. Never infer an email pattern.
4. Check applicable higher-priority sources for prior contact, drafts, replies, meetings, ownership, duplicate records, opt-outs, suppression, or conflicting active sequences.
5. Classify each contact path as named verified email, generic official inbox, contact form, directory-only, user-supplied, or unavailable. Do not call enriched, generic, or directory-only data personally verified.
6. Exclude stale, weak, duplicate, opted-out, non-authoritative, already-active-sequence, or unverifiable targets.
7. Rank qualified recipients by demographic fit, decision authority, ability to act, contact quality, relationship evidence, and freshness.

Log qualified and excluded candidates in both campaign records. Return a compact ranked table: rank; person/title; organization; recipient type; demographic-fit rationale; why they can act; relationship/duplicate state; contact path/classification; sources/date; recommended tailored ask; and status.

## 8. Personalize drafts

After the user approves a research queue or requests drafts, adapt the selected template direction for each recipient:

1. Tailor to both the user’s true profile and the recipient’s actual role, company priorities, and documented fit.
2. For sponsorship, connect the verified opportunity to the recipient’s plausible interests, state the exact support requested, and promise only substantiated benefits.
3. Use one or two truthful proof points. Do not invent relationships, qualifications, urgency, results, events, sponsor benefits, access, or metrics.
4. Make one concrete, low-friction ask. Do not combine a job request, sales pitch, favor, sponsorship request, and meeting request in one first touch.
5. Use a specific subject and default to 80–150 words for a cold email.
6. Show recipient/contact path, subject, exact body, why it is specific, facts needing confirmation, sources checked, template version, and `NOT SENT`.

## 9. Choose delivery method

After the requested `X` recipients are found, logged, de-duplicated, and approved for outreach, inspect the **current user’s** connected connectors for email-delivery capabilities. Check for mailbox draft/send connectors and relevant transactional-email, outreach, mail-merge, or automation services, such as Resend, Gmail, Outlook, Brevo, Mailchimp, Instantly, Lemlist, MixMax, Mailgun, Postmark, Power Automate, and equivalent connected tools.

Report each relevant option as `connected`, `available but not connected`, `temporarily unavailable`, or `not available for this user`. Do not use a fixed list or the assistant’s own integrations.

Present available choices and ask the user to choose after explaining fit, trade-offs, recordkeeping, setup, expected sending volume, personalization needs, attachments, scheduling, tracking, and account-limit constraints. Do not create an automation, mail merge, sequence, draft queue, or send until the user chooses a method and explicitly approves the exact external action.

| User need | Default recommendation | Escalate when |
| --- | --- | --- |
| Small, highly personalized outreach | Individual email drafts/sends from the user’s mailbox | Standardized fields, larger queue, or scheduled follow-up is needed |
| Small-to-moderate batch with simple fields | Native mail merge in the user’s office suite | Native merge cannot support needed fields, attachments, approvals, logging, or compliance controls |
| Moderate batch needing richer personalization, follow-ups, templates, or analytics | Connected outreach/delivery MCP if available and suitable | It lacks required consent/suppression controls or does not meet requirements |
| Repetitive workflow with conditional logic, approvals, cross-system updates, or scheduling | Dedicated Power Automate flow in a suitable Microsoft 365 environment | Native mail merge fully meets the need, or Power Automate is unavailable/unnecessarily complex |
| No suitable sending method connected | Provide a duplicate-checked send-ready queue | The user asks to connect a service or approves a specified workflow setup |

Prefer the least complex option that fully meets the requirement. If native mail merge is enough, recommend it rather than a plug-in or custom automation. Recommend a plug-in only for a specific native limitation. Recommend Power Automate only when its automation, governance, approval, or synchronization benefit justifies additional setup.

## 10. Mail merge and Power Automate

Before native mail merge or a plug-in:

1. Confirm sender identity, sending domain, reply-to address, spreadsheet source, merge fields, template version, recipient count, attachments, and schedule.
2. Validate every row: approved recipient, legitimate contact route, no opt-out/suppression, no duplicate/conflicting sequence, and all required fields present.
3. Render and show representative previews. Remove unsafe or incomplete rows rather than sending malformed messages.
4. Use only the user-approved recipient set. Do not expand it, infer addresses, or add contacts during delivery.
5. Log method, template version, sender account, batches, timestamps, recipient status, and observed outcomes in both records.

Before proposing a Power Automate flow, define the smallest safe flow in plain language: trigger, data source, eligibility checks, approval gate, sending action, error handling, logging, and stop conditions. Example: a manually triggered flow reads spreadsheet rows marked `approved`, sends through the selected Outlook account, and writes result/timestamp back to the records.

Do not create, enable, or run a flow without showing complete behavior, identified connected accounts/data destinations, and obtaining explicit approval. Build approval, suppression, and duplicate checks into it; never build a flow that bypasses provider controls or bulk-sends unreviewed messages.

## 11. Limits, sending, and follow-up

Treat account and provider sending limits as hard operational constraints, not targets to work around. Before scheduling or sending any batch:

1. Check applicable provider, account, workspace, and plan limits where a connected service exposes them or official documentation can be verified. Limits may vary by provider, account age/reputation, subscription, authentication, and recipient type.
2. Ask for total recipient count, daily cadence, and deadline. Choose a conservative batch size and spacing within verified limits, leaving room for ordinary account use.
3. Never bypass or recommend bypassing spam controls, quotas, authentication requirements, unsubscribe requirements, or consent/opt-out rules.
4. Avoid sudden high-volume sending from a new or low-history mailbox. Prefer slower approved batches or individual outreach if deliverability is uncertain.
5. Stop and hold the queue if the provider reports a limit, warning, failure, bounce pattern, spam complaint, suppression, or account restriction. Report observed state and ask for direction.
6. Do not guarantee delivery or inbox placement. Provider acceptance supports `sent`, not `delivered` or inbox placement.

For email drafts, place only the exact shown, duplicate-checked draft and report `placed`, never `sent`. Send only after recipient-specific approval of exact current content. Immediately before sending, re-check recipient, subject, body, attachments, signature, send time, opt-out/suppression state, duplicate status, and limits.

Default follow-up policy: no more than two follow-ups, 5–7 business days apart, then hold the target unless the user specifies otherwise or material new information exists. Report only observed outcomes: `placed`, `sent`, `delivered`, `failed`, or `uncertain`. Update both records after material action when connected and authorized, preserving prior statuses and versions.

## Stop conditions

Stop and ask for direction when sender profile, target demographic, primary ask, requested `X`, opportunity facts, promised benefits, template selection, or claims are materially ambiguous; when no legitimate contact route exists; when a target has opted out or is in a conflicting sequence; when external record/workflow creation lacks explicit approval; when a required connector needs authorization; or when a send lacks recipient-specific approval.
